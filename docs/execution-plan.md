## What you get at the end
A **normal installable desktop app**, not Docker. Primary target is **macOS**: a `.dmg` for Apple Silicon and Intel. CI also builds Windows (`.exe`) and Linux (`.AppImage`, `.deb`).

- Installers are built by **GitHub Actions** on a release tag and attached to the repo's **Releases** page.
- **Unsigned macOS build (default):** ad-hoc signed so it runs on Apple Silicon. On first launch macOS blocks it; you open **System Settings → Privacy & Security → Open Anyway** once. This path is labelled "unsigned build" in the release notes.
- **Signed + notarized build (optional, Apple's recommended path):** turned on by adding five repo secrets: `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` (needs a paid Apple Developer account). With them, the app opens with no warning.
- Size roughly 90–120 MB. No Docker: a GUI app gains nothing from it and loses the native file picker and clipboard.

## A. Specifications (frozen in Wave 0, every agent builds against these)

### A1. Supported file format
- **Supported:** Password Safe **V3** files: tag `PWS3`, header Version field major byte `0x03`, minor `0x00`–`0x11` (Password Safe 3.01 through spec v3.31, format `0x0311`).
- **Newer V3 minor version** (`0x0312`+): opens **read-only** with a banner "Made by a newer Password Safe; editing disabled to avoid losing data." Export still allowed.
- **V4 and anything without the `PWS3` tag:** rejected with `UNSUPPORTED_FORMAT` ("This is not a Password Safe V3 file. V4 files are not supported."). The app never opens such a file for writing, never creates a `.plk` for it, and never writes to its path.
- **V1/V2 (`.dat`) files:** out of scope, same `UNSUPPORTED_FORMAT` error.
- **YubiKey-protected V3 files:** out of scope for v1. The YubiKey marker (header field `0x12`) is inside the encrypted part, so it can't be detected before unlock; the wrong-password message therefore adds "If this file uses a YubiKey, this version can't open it."
- **Key-stretch iterations:** accepted range **2,048 to 2^24 (16,777,216)**. Above that: `UNSUPPORTED_FORMAT` ("This file uses more key-stretching rounds than this app supports"). On save, keep the file's value but raise it to at least **262,144**, matching Password Safe 3.68+ (spec §2.4).
  - **Planning estimates only** (Node 22, `crypto.createHash` loop, 4-core cloud VM, not the target hardware): 262,144 rounds ≈ 0.64 s; 2^20 ≈ 2.4 s; 2^22 ≈ 10 s; so 2^24 ≈ 40 s and 2^25 ≈ 80 s. 2^25 was too slow to accept.
  - **Budget and gate:** unlock at 262,144 rounds ≤ 1 s on an Apple Silicon Mac. The **release criterion is the benchmark on the macOS Apple Silicon CI runner** (WP2), not the cloud numbers above. WP2 also tries a faster loop over raw buffers; results go in `docs/benchmarks.md`.
  - **UX:** stretching always runs in a **worker thread**, so the window never freezes. If the file's rounds exceed 2^20, the unlock screen shows a progress bar with **Cancel** and the text "This file uses extra-strong key stretching; unlocking takes longer."
  - **Effect of the cap:** a valid file with more than 2^24 rounds (Password Safe allows setting very high values) is refused, not damaged. The message says so. The cap is fixed at 2^24 when contracts freeze. If the Mac benchmark later justifies a change, the constant in `src/shared/limits.ts`, the error message, the tests and this section change together in one lead-reviewed PR.

### A2. Round-trip contract
A save produces a new salt, IV, keys K and L, and random padding, so the **encrypted file is expected to differ** from the original (a collision is astronomically unlikely, not impossible, so no test asserts byte difference). Success is defined on the **decrypted field stream**:

1. **No-edit round-trip:** open → save → reopen gives a header field list and, per record, a field list where every field's `(type, data bytes)` is identical and in the same order, **except** the header fields we update on save: last-save time `0x04`, last-save application `0x06`, and `0x07`/`0x08` last-save user/host (only if the file already had them).
2. **Opaque bytes:** every field we don't decode keeps its original bytes exactly. A decoded field we did not edit also keeps its original bytes (untouched text is never re-encoded, so odd encodings survive).
3. **Field order:** kept as read. An edited field is replaced in place; a newly set field is appended before `END`.
4. **Duplicates:** never merged or dropped. A record with a duplicate *editable* field type opens **read-only** for that record (see A3).
5. **Record order:** kept as read; new records appended at the end.
6. **Framing under the V3 HMAC gap:** the V3 HMAC covers field data but not field type/length (spec §2.11, V4 §1.2.4.3). So the parser also checks framing itself: every length fits in the remaining decrypted bytes, blocks are 16-byte aligned, the header starts with Version and ends with `END`, each record ends with `END`, and the EOF block sits exactly on a block boundary. Any violation is `CORRUPT_FILE`.

**Tests, in two independent layers:**
- **Self-consistency (WP2):** `fieldStream(reopen(save(open(f)))) == fieldStream(open(f))` modulo the save-metadata fields. Useful, but it only proves we can read what we wrote.
- **Independent oracle (WP8):** the official **`pwsafe-cli` built from Password Safe tag `1.25.0`** (exact commit SHA recorded) reads every file we write. The test exports each file with `pwsafe-cli <file> --export=<out.xml> --xml` and compares **decoded values** field by field (UUID, group, title, username, password, URL, email, notes, times, entry count) against an expected-values JSON written independently from the fixture, not from our parser. It also runs the other direction: files **created by** `pwsafe-cli 1.25.0` via `--create` and `--add=<fields>` (with known contents) are opened by our app and compared to the same JSON. "The CLI opens the file" alone is never a pass. **Secrets in CI:** the passphrase is written to the CLI's stdin, never passed as `--passphrase` (which would appear in process listings and logs); shell tracing is off in oracle steps; exported XML stays in the job's temp directory and is never printed or uploaded as an artifact.

### A3. Record model and per-field decisions
Two layers in `src/shared/types.ts`:

```ts
type RawField  = { type: number; data: Uint8Array };      // exact bytes, in file order
type RawRecord = { fields: RawField[] };                  // END implicit
type Entry = {                                             // a view over one RawRecord
  uuid: string; title: string; group: string; username: string; password: string;
  url: string; email: string; notes: string;
  created?: Date; modified?: Date; passwordModified?: Date; expires?: Date;
  kind: 'normal' | 'alias' | 'shortcut' | 'aliasBase' | 'shortcutBase';
  flags: { hasHistory; hasTotp; hasAttachment; hasPasskey; hasCreditCard; hasCustomFields; extraFieldCount };
  editable: boolean; readOnlyReason?: string;
};
```
The vault keeps `RawRecord`s as the source of truth; edits write through to specific fields. Nothing is ever rebuilt from the `Entry` view. (The `password` value in `Entry` is only filled in main for a reveal or copy; lists sent to the renderer carry an empty string. See A4.8.)

| Field(s) (type) | v1 behaviour |
|---|---|
| UUID `0x01`, Group `0x02`, Title `0x03`, Username `0x04`, Notes `0x05`, Password `0x06`, URL `0x0d`, Email `0x14` | Shown and **editable** |
| Times `0x07 0x08 0x09 0x0a 0x0c` | Shown; `0x0c` modified and `0x08` password-modified updated on edit |
| Password history `0x0f` | **Preserved unchanged.** v1 does not append to history on password change; a flag shows history exists |
| Two-factor key and TOTP `0x1b`, `0x21`–`0x24` | Preserved opaquely; badge "Has 2FA (view in Password Safe)" |
| Attachments `0x25`–`0x29`, Passkeys `0x2a`–`0x2f`, Credit card `0x1c`–`0x1f`, QR `0x20`, Custom fields `0x30` | Preserved opaquely; badge shown |
| Policy, autotype, run command, shortcuts, protected flag, etc. (`0x0e 0x10–0x13 0x15–0x19`) | Preserved opaquely. **Protected entry `0x15` = 1 → record read-only** |
| Unknown / future / app-specific types (`0xc0`–`0xfe`, unassigned) | Preserved opaquely (spec §4.1 requires it) |
| Unknown **header** fields | Preserved opaquely |
| **Alias** (password `[[uuid]]`) and **shortcut** (`[~uuid~]`) entries | Shown with a link to their base entry; **read-only** in v1. Copy password resolves to the base's password |
| Base entry that has aliases or shortcuts | Editable; **delete is blocked** with "Other entries depend on this one" |
| Record missing mandatory UUID/Title/Password, or duplicate editable field, or invalid UTF-8 in an editable field | Preserved; **record read-only** with the reason shown |

**Rule:** nothing is ever silently dropped. If an edit could lose data, the record is read-only instead. The whole file is rejected only for the A1/A4 reasons. WP2 verifies each row against the spec text and against fixtures made with Password Safe 1.25.0 containing aliases, shortcuts, history, TOTP and an unknown `0xdf` test field. `pwsafe-cli --create/--add` makes the ones it can; the rest are made once in the Password Safe app, committed with their expected-values JSON, and noted in `docs/references.md`.

### A4. Crypto and parser safety (codec requirements)
Open sequence, in this order, with nothing decrypted returned before step 7:

1. **Size bounds:** file must be ≥ 232 bytes (the smallest possible valid V3 file) and ≤ **128 MB**, else `CORRUPT_FILE` / `TOO_LARGE`.
2. **Tag** `PWS3` else `UNSUPPORTED_FORMAT`.
3. **Iterations** within A1's range else `UNSUPPORTED_FORMAT`.
4. **Stretch key** (worker thread, cancellable), compare `SHA-256(P')` with `H(P')` using `crypto.timingSafeEqual`, else `WRONG_PASSWORD`.
5. **Decrypt K and L** (ECB), then the body (CBC). The ciphertext before EOF must be a multiple of 16 bytes and EOF must be present exactly once at a block boundary, else `CORRUPT_FILE`.
6. **Parse framing** (A2.6) with limits: field length ≤ 16 MB, ≤ 1,024 fields per record, ≤ 200,000 records. Any breach is `CORRUPT_FILE`.
7. **Verify HMAC** over all field data with `timingSafeEqual`, else `INTEGRITY_FAILED`. **Only now** are records built and returned.
8. **Secret handling (best-effort minimisation, not a guarantee of erasure):**
   - **What we do:** the master password is taken from the unlock field as bytes and held only in the main process in a `Buffer`. K, L, P' and decrypted field buffers are main-process `Buffer`s that we `fill(0)` when no longer needed and on lock. Passwords are never sent to the renderer in lists; they cross IPC only for an explicit reveal. Copy happens in main. On lock, the renderer drops all entry state and reloads its view, so no React state survives.
   - **What we can't promise:** JavaScript strings are immutable and garbage-collected, so any value that becomes a string (a revealed password shown in the UI, text typed into a field, values passed through IPC's structured clone, Chromium's own input buffers) may remain in memory until overwritten. We don't claim every plaintext copy is erased. This limit is written in the README's security section.
   - **Tested boundaries (WP7/WP9):** an IPC spy test proves no password value crosses to the renderer except in a reveal response; a test proves renderer state is empty after lock; a test proves owned key buffers are zero after lock.

**Error codes** (in `src/shared/ipc.ts`), each with its own message and none exposing decrypted data: `UNSUPPORTED_FORMAT`, `CORRUPT_FILE`, `TOO_LARGE`, `WRONG_PASSWORD`, `INTEGRITY_FAILED`, `LOCKED_BY_OTHER`, `FILE_CHANGED_ON_DISK`, `SAVE_FAILED`, `SAVED_DURABILITY_UNCONFIRMED`, `IO_ERROR`, `CANCELLED`.

**Twofish:** V3 only uses 256-bit keys (P', K and L are all 256 bits), so the required known-answer tests are the official 256-bit vectors, including the full 49-iteration chained test. 128- and 192-bit vectors also run because they are cheap, but correctness for this format depends only on 256-bit.

**Malformed-input tests** (WP2, WP8): truncated at every block boundary of a fixture, length field overflowing the buffer, length = 0xFFFFFFFF, missing `END`, missing EOF, duplicate EOF, EOF not block-aligned, header not starting with Version, a flipped bit in data (must be `INTEGRITY_FAILED`), a flipped bit in a length byte (must be `CORRUPT_FILE` or `INTEGRITY_FAILED`, never a crash or a hang), iterations = 2^32−1 (refused at step 3, before any stretching).

### A5. Save, backup and restore
**Principle:** the database replace is the single commit point. Backups are staged beforehand and only committed after it succeeds, so **a failed save leaves the database and every existing backup generation exactly as they were**.

Paths: `db` = the resolved real path (symlinks resolved at open and stored); `dir` = its directory; `tag` = random suffix per save.

1. **Conflict check:** stat and hash `db`; if size, mtime or SHA-256 differ from what we read at open (or last saved), abort with `FILE_CHANGED_ON_DISK` (see Save As below).
2. **Serialize in memory** with fresh salt, IV, K, L and padding; **re-parse in memory** and assert the A2 contract against the current model.
3. **Write new file:** `dir/.name.tag.new`, created with `O_EXCL` and `db`'s permission bits; write, `fsync`.
4. **Re-read `.new` from disk** and verify (HMAC plus A2).
5. **Stage backups (no existing backup is touched yet):** copy `db` to `dir/.name.tag.bak-staged` and `fsync` it. Existing `.bak`, `.bak2`, `.bak3` stay as they are.
6. **Final check:** `lstat(db)` must still be a regular file with the **same device and inode** and the same size, mtime and hash as at open (or last save), and `realpath` of the path the user opened must still resolve to `db`. Otherwise abort with `FILE_CHANGED_ON_DISK`. (A short gap remains between this check and step 7. `rename` replaces the directory entry itself and does not follow a symlink placed at `db`, so a swap can't redirect our write elsewhere. The `.plk` is cooperative: it only stops apps that honour it. The README says both.)
7. **Commit:** `rename(.new → db)`. Atomic on APFS/HFS+/ext4. On Windows, `MoveFileEx(REPLACE_EXISTING)` with 3 retries on `EPERM`/`EBUSY`.
8. **Post-commit, backups (journaled, idempotent):**
   - Before step 7, write `dir/.name.rotation.json` and `fsync` it: the SHA-256 of the current `.bak` (`h1`), `.bak2` (`h2`), the staged copy (`hs`), and the three planned moves in order: `.bak2 → .bak3` (expect `h2`), `.bak → .bak2` (expect `h1`), `.bak-staged → .bak` (expect `hs`). A missing generation is recorded as "none" and its move skipped.
   - Each move runs **check, then act**: if the destination already has the expected hash, the move is done (and a leftover source with the same hash is deleted); else if the source has the expected hash, rename it; else stop and keep every file (see "unknown state").
   - After the last move, delete the journal.
9. **Post-commit, durability:** `fsync(dir)` (macOS/Linux).
10. Update the stored size/mtime/hash; clear the dirty flag; delete any leftover staged files for this `tag`.

**Failure outcomes (what the user sees and what is on disk):**
| Fails at | On disk | User sees |
|---|---|---|
| 1, 6 | Nothing changed; staged files deleted | "The file was changed by another app." Options: **Save As…**, **Reload (discard my changes)**, **Cancel** |
| 2–5 | Database and all backups unchanged; staged files deleted | "Save failed at step N: reason." Changes still in memory, still unsaved |
| 7 | Database and all backups unchanged (rename is all-or-nothing) | Same as above |
| 8 (any backup move, or process death between moves) | **New database saved.** Journal present; every generation still exists somewhere (in its old or new name); the staged copy is kept until its move is confirmed | "Saved. Backup rotation didn't finish; it will complete next time you open this file." |
| 9 (`fsync(dir)`) | **New database in place**, but the OS couldn't confirm it will survive a power cut | `SAVED_DURABILITY_UNCONFIRMED`: "Saved, but macOS couldn't confirm the save is fully written to disk. Your previous version is in the backups." Not reported as a failed save |

**Recovery on open:** leftover `.new` files are deleted (they were never committed). If a rotation journal exists, step 8 is re-run from the journal; because every move checks before it acts, running it once, twice or after a crash mid-recovery gives the same final state. **Unknown state** (a file present whose hash matches nothing in the journal): nothing is moved or deleted, the journal is kept, and a banner lists the backup files so you can restore manually. A leftover `.bak-staged` with no journal (crash before step 7) is deleted only if its hash equals the current `db`, otherwise kept and reported. Recovery actions are logged and shown once as an info banner.

**Known limit:** Node's `fsync` on macOS doesn't issue `F_FULLFSYNC`, so a power cut right after a save could still lose drive-cached data. Step 4's re-read plus the backup generations cover this; a native `F_FULLFSYNC` helper is a v1.1 candidate.

**Retention:** **3 generations** (`.bak`, `.bak2`, `.bak3`), each an encrypted copy under the master password that was current when it was made.

**Save As…** (from the conflict dialog or the File menu), native save dialog:
| Destination | Behaviour |
|---|---|
| **Same as the active file** | Treated as a normal Save (steps 1–10) |
| **New path** (doesn't exist) | Take the destination's `.plk` first (`O_EXCL`). Steps 2–4 write and verify `.new`; commit with `link(.new, dest)` then remove `.new`: `link` fails if `dest` appeared meanwhile, so we never clobber a file created in the gap (then: `FILE_CHANGED_ON_DISK`). No backups exist yet; the first later Save creates `.bak`. |
| **Existing file**, not locked | The OS dialog asks to replace it. We then take its `.plk`, record its size/mtime/hash/inode as the "as read" state, and run the full steps 1–10 against it, so the file being replaced becomes **its** `.bak` and its existing backups rotate. It doesn't need to be a psafe3 file; if it isn't, the backup still keeps it. |
| **Existing file with a `.plk`** (someone has it open) | Refused: "That file is open in another app." Nothing written |
| **Another file open in this app** | Same as locked (only one vault is open at a time, so this is its own `.plk`, refused the same way) |

On success: the **destination becomes the active database**, the old path's `.plk` is released, and the destination goes to the top of Recent files. The old file is left untouched. On failure: the destination's `.plk` is released and the active database stays the old one.

**Restore:** File → **Restore from backup…** lists the backups with their dates. Picking one asks for its password, opens it **read-only** to preview, then **Restore this version** replaces the current file through steps 1–10 (so the current file becomes `.bak` and nothing is lost).

**Fault-injection tests (WP6/WP8):** an injected failure **and a simulated process death** at every individual operation of steps 1–10 (each copy, write, `fsync`, rename, journal write, and the directory `fsync`), using an injectable file-system layer. Each test asserts the exact on-disk state from the table above: the database content, **every backup generation's content**, and which staged/journal files exist. It then runs open-time recovery, **runs it a second time**, and also kills recovery midway and reruns it, asserting the same final database and backup generations each time.

### A6. `.plk` lock file (platform-specific)
**Common to all platforms** (same in all three pinned source files): lock name `foo.psafe3` → `foo.plk` (suffix replaced); content `user@host:pid` written as wide characters, which means **UTF-32LE on macOS and Linux** and **UTF-16LE on Windows**. Our reader accepts ASCII, UTF-16LE and UTF-32LE; our writer uses the platform's native encoding. Held from open-for-editing until close or quit; removed on normal exit.

| Platform | How Password Safe decides a lock is live (pinned source) | What our app does |
|---|---|---|
| **macOS** (primary; `src/os/mac/file.cpp` @ 1.25.0) | Create with `O_CREAT \| O_EXCL`; **any existing `.plk` means locked**. There is **no automatic stale-lock removal**. | Create with `O_EXCL`. Any existing `.plk` is treated as locked. **We never delete one automatically.** The dialog shows who/where from the file and offers **Open read-only** or **Remove lock and open…** (explicit second confirmation: "Only do this if Password Safe isn't running with this file on user@host"). Removing our *own* lock (same user, host and our current PID) is allowed silently. |
| **Linux** (`src/os/unix/file.cpp` @ 1.25.0) | `O_EXCL`; removes an orphan lock only if **same user and same host and the PID no longer exists**. | Same rule as Password Safe, and only on local filesystems. On network filesystems we never auto-remove. Everything else as macOS. |
| **Windows** (`src/os/windows/file.cpp` @ 3.72.2) | Liveness comes from an **open handle** held with `FILE_SHARE_READ` only; another instance's `CREATE_ALWAYS` fails with a sharing violation while the handle is open, and succeeds (overwriting) once the owner has exited. | **v1 opens every vault read-only on Windows** (browse, search, copy, export). Node can't hold a handle with that share mode without a native module, so Password Safe for Windows would see our lock as free and a warning can't prevent lost updates. Editing is enabled on Windows only in a later version that ships a native share-mode lock **and** passes the A6 interop test against Password Safe 3.72.2. The read-only banner on Windows says why. |

- **Network volumes** (SMB, AFP, NFS; macOS detected from `statfs` filesystem type): `O_EXCL` isn't reliable there, so a banner says "File is on a network drive; make sure no one else has it open." No automatic lock removal on any platform.
- **Can't create the lock** (permissions, read-only volume): open read-only with a banner explaining why.
- **Read-only mode:** editing, delete, save and restore are disabled; browse, copy and export work.
- **Tests:** unit tests for every row with byte-exact lock fixtures in both encodings; a Windows CI test proves no write path is reachable (save, delete, restore, Save As all refused). **Interop test on the primary OS (release gate):** with **Password Safe 1.25.0 for macOS**, (a) open the file in Password Safe, then in our app → our app reports it locked and offers read-only; (b) the reverse → Password Safe reports it locked; (c) quit ours normally → Password Safe opens it without a lock prompt. `pwsafe-cli` isn't used for lock tests because it isn't confirmed to take the same lock path.

### A7. XML export
- **Format:** Password Safe XML, validated against the official `pwsafe.xsd` from tag `1.25.0` in CI with `xmllint`.
- **Scope:** all entries, or the current group (with subgroups). Read-only records are included.
- **Fields exported:** those the schema defines for data we decode (group, title, username, password, URL, email, notes, times, UUID). Fields with no XML equivalent (attachments, passkeys, unknown types) are omitted, and the dialog shows how many entries have fields that won't be exported. Alias and shortcut entries export in their stored `[[uuid]]` / `[~uuid~]` form.
- **Destination:** native Save dialog, default `~/Downloads/<db-name>-export-YYYYMMDD.xml`. Overwriting an existing file uses the OS's own overwrite confirmation. Written via temp file + rename, permission `0600` (owner only).
- **Plaintext handling:** the warning and "I understand" checkbox stay mandatory; after export a toast shows **Reveal in Finder** and a reminder to delete it. The app never auto-deletes the file.
- **Tests:** fixture data with `& < > " '`, `]]>` inside a value, multiline notes, empty fields, nested groups (`a.b.c`, plus a group name containing a literal dot, escaped the way Password Safe itself does, verified against a Password Safe-made export), non-ASCII text and emoji, very long values, 1,000 entries. Our XML is also imported with `pwsafe-cli 1.25.0 --import --xml` into a new safe and compared value by value.
- **Importer acceptance (release gate):** this app's exported XML is imported into **KeePass 2.x** (latest release at test time, "Password Safe XML" importer) and **Bitwarden** (web vault, "Password Safe (xml)" importer). The product versions, entry counts and spot-checked values are recorded in the release notes. Schema validation alone doesn't count as a pass.

## B. UI behaviour (fills the gaps between mockups; WP3 acceptance criteria)

1. **Generator state:** defaults are length 20 with uppercase, lowercase, digits and symbols **on**, avoid look-alikes off, and **"Use at least one of each selected type" on** (an explicit checkbox; when on, a password missing a selected type is discarded and a new one drawn, which keeps every valid password equally likely). The preview and strength label are always computed from the current settings, and at least one set must stay on. Settings are remembered between sessions. (The mockup's checkboxes are meant to be ticked; the built UI and its tests make the visible settings, sample and strength label agree.)
2. **Locking:** idle timeout default **5 min** (setting: 1–60 min). Lock on **sleep** and on **screen lock**: always on. **Lock on minimize**: a setting, default **off**, because it would lock every time you minimise to switch apps; it's listed next to the idle setting with the text "Lock when the window is minimised". The **locked screen** shows the file name, the master password field and **Unlock**. On lock, the renderer discards all entry state and visible field values and the main process clears its owned secret buffers (best-effort, per A4.8).
3. **Unsaved changes:**
   - **Auto-lock** (idle, minimize, sleep, screen lock) with unsaved changes: the main process re-encrypts the current state **in memory** as a psafe3 blob under the same master password, then clears its owned plaintext buffers. After unlock, the changes are back and still marked unsaved. Nothing is written to disk unless you choose to save.
   - **Manual lock, Close, Quit, Open another file** with unsaved changes: dialog **Save / Don't save / Cancel**.
   - **Quit while locked** with unsaved changes: dialog **Unlock and save / Quit without saving / Cancel**.
   - Pending deletes count as unsaved changes; the header shows "Unsaved changes (3)".
4. **Backup copy in the Delete dialog:** "Removed from the file when you save. Each save keeps the previous 3 versions as backups, which you can restore from File → Restore from backup." Matches A5.
5. **Clipboard:** the 30 s timer **starts at copy**. The toast counts down. The clipboard is cleared at 0 **only if it still holds the copied value**, and is also cleared (same condition) on lock and quit. Copying again restarts the timer.
6. **Reveal:** passwords are **masked by default** everywhere, including the editor for existing entries. Show/Hide toggles per view. Reveal resets to masked on selecting another entry, closing the editor, saving and locking. A freshly generated password in the generator preview is visible (it isn't saved yet).
7. **Window and accessibility:** minimum window **960 × 620**. Below 1,180 px wide the Groups sidebar collapses behind a toggle; the details pane never drops below 360 px. Visible 2 px focus ring on every control; every icon-only button has an accessible name; full keyboard use (Tab order: toolbar → groups → list → details); ⌘F search, ⌘S save, ⌘L lock, ⌘N new entry, Delete key on a selected entry; checked with **VoiceOver** on macOS.
8. **Read-only states:** banner at top for read-only files (A1, A6) and a lock icon plus reason on read-only records (A3).
9. **Slow unlock:** progress bar and Cancel for files over 2^20 rounds (A1).
